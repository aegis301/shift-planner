## Context

R1 and R2 had uncertainty about scope, not feasibility. R3 has genuine technical uncertainty:
with 18 rule classes, statutory limits, wishes, no-gos, property requirements and a fairness
objective, **nobody knows yet whether the constraint set is solvable on a realistic month** — or
what a solution looks like when it is.

Carrying that uncertainty through #74 (worker infrastructure), #75 (model) and #76 (UI) is the
expensive way to find out. This issue retires it cheaply first.

**This is a spike. The deliverable is knowledge, not code.** The branch is never merged.

## Timebox

One working day. If the answers are not clear by then, that is itself the finding — report it
and we re-scope #75 rather than extending the spike.

## Scope

A single throwaway script (`backend/scratch/solver_spike.py`, git-ignored or on a branch that is
deleted afterwards) that:

1. loads a month generated by the fixture seed (#24) for each of the three profiles
2. builds a CP-SAT model directly — no `SolverRun`, no worker, no persistence, no API, no UI
3. solves it and prints the resulting roster as a table, plus the objective breakdown
4. is allowed to be ugly, hard-coded and untested

The **findings note** is the actual output: `docs/rollout/solver-spike-findings.md`, committed to
`main` on its own, which #75 then builds on.

## Questions the spike must answer

Write each answer into the findings note with the evidence behind it:

1. **Feasibility.** Does `comfortable` produce a full assignment? Does `tight`? What exactly
   binds first when it does not — rest periods, duty limits, property requirements, no-gos?
2. **Solve time.** Wall clock per profile. Expectation is seconds; if it is minutes, something is
   modelled wrong and that finding changes #75.
3. **Weight ordering.** Run `tight` at least twice with different weightings — once with unfilled
   slots dominant, once with no-go violations dominant. Print both rosters. Which one would a
   planner rather receive? This is a product decision and it should be made by looking at two
   real outputs, not at a whiteboard.
4. **Severity mapping.** Confirm that mapping `error` → hard constraint and `warning` → penalty
   behaves sensibly. Specifically: does treating every `warning` as a penalty leave the model
   solvable on `tight`, and does promoting one of them to hard make it infeasible?
5. **Infeasible profile.** Does the slack-variable approach return a usable partial assignment,
   and can you identify which constraints bound it?
6. **Determinism.** Run the same input twice with default solver parameters. Do you get the same
   roster? Then repeat with `num_search_workers=1` and a fixed `random_seed`. Record what it
   takes to make a run reproducible — a planner who re-runs and gets a different plan will not
   trust the feature.
7. **Warm start.** Pre-assign half the month and pass it via `AddHint`. Does the solver respect
   it, and what does it cost in solve time?
8. **Which of the 18 rules resist linearization?** List them explicitly. Those are the ones that
   stay post-solve checks in #75, and knowing the list up front is half of that issue.

## Out of scope

Anything that survives the spike. Do not build `SolverRun`, do not touch `services/rules/`, do
not add `to_cpsat` implementations to production rule classes, do not open a PR against `main`
with spike code. The only thing that lands on `main` is the findings note.

## Acceptance criteria

- [ ] `docs/rollout/solver-spike-findings.md` answers all eight questions with concrete numbers
      and, where relevant, pasted output.
- [ ] It names the rules that resist linearization.
- [ ] It states a recommended weight ordering and the reasoning from the two real outputs.
- [ ] It states the solver parameters needed for reproducibility.
- [ ] It lists any finding that should change the scope of #75, explicitly, so #75 can be edited
      before it starts.
- [ ] No spike code is merged.
